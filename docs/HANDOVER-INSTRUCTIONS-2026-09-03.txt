WHAT THIS IS

Eight migrations to run, in order, in the EZER Supabase project. They unlock
features that are already built, tested and pushed to the TusharPanwar branch
but which currently render a "not switched on yet" state because their tables
do not exist.

Nothing here has been run against the database. Nobody but you applies schema
changes to this project.

    migrations/075_ess_notification_catalogue.sql
    migrations/079_group_profile.sql
    migrations/082_access_foundation.sql        <-- 084 will not work without it

    migrations/085_wall_of_fame_seed.sql
    migrations/086_shoutouts_and_feed.sql
    migrations/087_social_and_inbox.sql

Order matters in exactly two places:

  * 082 BEFORE 084. 084 calls can() at five sites and 082 creates it. Run
    084 first and every access check in the Wall of Fame fails closed.

    082 also creates explain_access(). Nothing in 084-087 actually calls
    that one — wof_explain_access(), which 084 defines itself, is the one in
    use. explain_access() is there because the bundle's brief named it and a
    future route may expect it. Said plainly so you know which of the two is
    load-bearing.

  * 084 BEFORE 085, 086 and 087. Those three ALTER tables that 084 creates
    and seed a catalogue 084 defines.

There is no 083. The number is deliberately skipped — see section 5.

Every file is written to be safe to run twice: CREATE TABLE IF NOT EXISTS,
ADD COLUMN IF NOT EXISTS, CREATE OR REPLACE FUNCTION, ON CONFLICT DO NOTHING.
If a run half-fails, fix the cause and run the whole file again.

3. AFTER THE MIGRATIONS — activation, once per company
--------------------------------------------------------------------------------

The Wall of Fame does nothing until it is switched on. This is deliberate:
the module is not self-serve, and only EZER activates it.

    -- 1. provision the defaults
    select seed_wall_defaults('<company_uuid>', '<hr_head_employee_uuid>');
    select seed_shoutout_categories('<company_uuid>');

    -- 2. EZER's own Super Admin flips the master switch
    update wall_config set module_enabled = true
     where company_id = '<company_uuid>';

From then on the company's Wall Owner does everything else from the admin
console. No further SQL.

The PMS also needs one call per financial year to create its periods:

    select pms_generate_periods('<policy_id>', '2026-27', '2026-04-01');

Nightly job (Vercel cron or a Supabase scheduled function):

    select generate_service_milestones(id) from companies;

    NOTE: the bundle this came from wrote that as "... from companies where
    is_active". companies.is_active does not exist in this database — I
    checked. The filter is removed rather than swapped for a guess, because
    guessing which column means "live" could silently skip real companies
    every night and nothing would look broken. If there is a liveness
    column, tell me and I will put it back.

5. WHY THERE IS NO 083
--------------------------------------------------------------------------------

The Wall of Fame bundle assumed a migration 083 providing can(uuid,text,text)
and explain_access(). It is in neither this repository nor the database.

can() is genuinely load-bearing: 084 calls it at five sites. explain_access()
is called nowhere in 084-087 and is provided for completeness.

Rather than invent a second permission system, 082 reads the one this app
already has and populates: ess_accounts, ess_roles, ess_user_roles and
role_permissions (module + NONE/VIEW/EDIT/FULL). can() is a reading of that
model. Two sources of truth about who may do what is the worst possible
thing to have two of.

The number 083 is left free in case the original ever arrives.

ONE QUESTION ON 082, and it is the only assumption in that file that would
silently WIDEN access if I have it wrong:

    is_ezer_staff() identifies EZER's own staff as
        ess_roles.role_code = 'ADMIN_SUPER'  with an ACTIVE ess_account.

    That is the code seeded in migration 027. If EZER staff are identified
    some other way, tell me and I will change it. Everything that only EZER
    may do — activating the module for a company — hangs off that one check.

--------------------------------------------------------------------------------

Run these after the eight migrations. Every one should return a row.

    -- 082: the access floor
    select count(*) from access_permission_map;              -- expect 20
    select can(null, 'wof.view', 'self');                    -- expect false

     where table_schema='public' and table_name like 'wall%';        -- expect 5+
    select count(*) from wall_permissions;                   -- expect 19

    -- 084: the rule that must never move
    select conname from pg_constraint
     where conrelid = 'wall_config'::regclass
       and pg_get_constraintdef(oid) ilike '%payout_linkage%';
    -- must return a CHECK pinning payout_linkage = false

    -- 086 / 087
    select count(*) from shoutout_categories;                -- 0 until seeded
    select count(*) from information_schema.columns
     where table_name='recognition_comments'
       and column_name in ('parent_comment_id','mentions');  -- expect 2

    -- 087: no approval may enter the recognition inbox
    select pg_get_constraintdef(oid) from pg_constraint
     where conrelid = 'wall_inbox_events'::regclass
       and pg_get_constraintdef(oid) ilike '%event_type%';

    -- 075 / 079
    select count(*) from ess_notification_catalogue;
    select count(*) from company_groups;

If any of those fail, stop and tell me what the error was rather than

--------------------------------------------------------------------------------
7. THE TWO RULES THE SCHEMA ENFORCES ON PURPOSE
--------------------------------------------------------------------------------

RECOGNITION NEVER TOUCHES PAY. wall_config.payout_linkage is pinned false by
a CHECK constraint, mirroring the locked PMS decision that performance
management here is developmental only. No setting unlocks it. Please do not
add a column, a report or an export that connects recognition points, badges
or awards to compensation — if a requirement seems to ask for it, raise it.

THE DIRECT CHANNEL CARRIES APPRECIATION AND NOTHING ELSE. wall_messages is
not a chat table. A note requires a category, the recipient gets exactly one
thank-back, and there is no path to an open thread. That is written into
send_appreciation() and thank_for_appreciation(). Free-form messaging inside
an HRMS is a harassment vector and a records-retention problem, and HR ends
up owning both. If somebody asks for general chat, it is a different product
with a different risk profile.


--------------------------------------------------------------------------------
8. IF SOMETHING GOES WRONG
--------------------------------------------------------------------------------

42501, insufficient privilege, on a config table write
    The connection has no acting employee. The write triggers depend on it:
        select set_config('app.current_employee_id', '<uuid>', true);
    For a migration or a seed run, set app.service_context to 'true' instead
    — enforce_wall_admin() lets service jobs through on that.

PGRST205 or 42P01, relation does not exist
    A migration did not run, or ran into an error partway. The files are
    idempotent; run the whole file again.

PGRST202, could not find the function
    Either the function is genuinely absent, or you called it with different
    arguments. Check pg_proc as in section 2 before concluding it is missing
    — I made that mistake twice while preparing this.

Everything reads as empty but nothing errors
    Almost always wall_config.module_enabled is still false, or
    seed_wall_defaults() has not been called for that company. The screens
    are built to show an honest "not switched on yet" rather than a blank.

CHANGES.md in this folder explains every code change behind these
migrations, and what breaks if a particular one is skipped.
