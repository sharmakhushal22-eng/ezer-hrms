1. WHAT IT CREATES
--------------------------------------------------------------------------------

    game_invites        who asked whom to play what, and what came of it
    game_sessions       one row per match: the two players, the seed, the
                        result
    game_score_shares   a result somebody chose to share

    funzone_current_employee()   reads app.current_employee_id
    accept_game_invite()         turns an invite into a session
    finish_game()                records the result — see section 4
    share_game_score()           shares one, and notifies whoever it names

No seed data, and nothing to call afterwards. The channel is empty until
somebody sends an invite, which is the correct empty.

A CORRECTION I MADE BEFORE SENDING THIS. 090 originally called
wof_current_employee(), which ONLY 084_wall_of_fame.sql defines. That would
have made the Fun Zone silently depend on the Wall of Fame: the functions
would have been created cleanly and then failed at the first call with
"function wof_current_employee() does not exist", because plpgsql does not
validate a body until it runs. Nothing would have surfaced until somebody
accepted a game invite.

It now resolves the caller itself, with its own copy of that one line. Two
unrelated break-time features should not be coupled by a function name.

--------------------------------------------------------------------------------
4. THE PART THAT IS WORTH UNDERSTANDING — WHO DECIDES WHO WON
--------------------------------------------------------------------------------

Live games run over Supabase Realtime broadcast, client to client, with no
server in the loop. Only the start and the finish reach the database.

TIC-TAC-TOE IS REPLAYED. finish_game() walks the move list and derives the
winner itself. Nine squares and eight lines is cheap, so no client is
believed.

MEMORY MATCH AND TRIVIA ARE SETTLED BY AGREEMENT. Both depend on a seeded
shuffle, and reimplementing that in plpgsql to check a break-time game would
be a third copy of the same logic drifting from the other two. So each client
reports its result, the first claim is parked in pending_claim, and the second
must match it.

  * One player alone cannot post a result. They can only leave the game
    unfinished, which gains them nothing.
  * Two clients that disagree end the session ABANDONED rather than picking a
    winner — a disagreement means one of them is wrong and there is no way to
    tell which.

If you see ABANDONED rows, that is the design working, not a fault. Somebody
closed a tab, or two clients disagreed.


--------------------------------------------------------------------------------
5. REALTIME — NOTHING TO ENABLE
--------------------------------------------------------------------------------

I tested it against this project rather than assuming: subscribing with the
anon key returns SUBSCRIBED and a broadcast echoes back in about 2.6 seconds.
It works as configured.

This is the first use of Supabase Realtime in the app — the inbox deliberately
polls — so if you ever tighten Realtime settings at the project level, this is
the feature that would notice. Nothing else uses it.


--------------------------------------------------------------------------------
6. A DECISION I NEED FROM YOU — RLS
--------------------------------------------------------------------------------

The three tables have no policies and I did not write them.

The stakes are the lowest of anything I have handed over — it is tic-tac-toe.
But "who has been playing games with whom, and when" reads badly in a
workplace, and scoping it costs nothing.

What I would write:

    game_invites        SELECT where the reader is from_employee or
                        to_employee; INSERT where from_employee is them
    game_sessions       SELECT where the reader is host or guest
    game_score_shares   SELECT where the reader is shared_by, or is named in
                        shared_with

The house default USING (true) would let anybody read every invite and every
game in the company.

The three functions are SECURITY DEFINER and check the caller themselves, so
writes are already gated whatever the policies end up saying. This is about
reads.


--------------------------------------------------------------------------------
7. NO PRIZES, AND NOTHING TO RECONCILE
--------------------------------------------------------------------------------

There is no link to recognition, the Wall of Fame leaderboard, performance or
pay. Results are stored and nothing ranks them, deliberately. A game that
counts towards something stops being a game.

If somebody later asks for a Fun Zone leaderboard, that is a product decision
rather than a schema one — the rows are already there.
