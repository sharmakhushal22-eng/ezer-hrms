5. A DECISION I NEED FROM YOU — the ESS inbox
--------------------------------------------------------------------------------

inbox_conversations and inbox_messages EXIST, but reading them as anon gives:

    42501 -- permission denied for table inbox_conversations
    hint: Grant the required privileges to the current role with:
          GRANT SELECT ON public.inbox_conversations TO anon;

I read 080_ess_inbox.sql: it issues no GRANT and creates no RLS policy. So the
tables were created without either and PostgREST cannot reach them. Every
other table in the project is readable, so something grants by default and
these two missed it -- I cannot tell from outside which.

I have NOT written a migration for this, on purpose. The house rule is that a
new table's RLS policy is your decision rather than something copied from an
older file, and an inbox is exactly the wrong place for an allow-all default:
these rows are private messages between named employees.

Three options, worst to best as I see it:

  1. GRANT SELECT ... TO anon, no RLS.
     Every employee can read every conversation in the company. Please do not.

  2. Grants plus RLS scoped to participants -- a row is visible when the
     reader is its sender or its recipient. This is what the feature assumes,
     and what I would write if you tell me to.

  3. All inbox reads through a SECURITY DEFINER function, nothing granted
     directly. Tightest, and the most work.

Tell me which and I will write the file. Until then the ESS inbox stays dark,
which is the correct failure -- it fails closed, not open.

6. WHAT DATA IS AND IS NOT IN THESE FILES
--------------------------------------------------------------------------------

Worth being exact about, because "run the migrations" and "the feature works"
are not the same sentence here.

SEEDED AUTOMATICALLY, the moment you run the file:

    082   access_permission_map      ~21 rows   the permission catalogue
    084   wall_permissions           ~18 rows   Wall of Fame permission codes
    087   wall_permissions           ~5 rows    the social/inbox additions

    Those are catalogue rows -- codes and labels the app looks up. They are
    not company data and they are the same for everybody.

NOT SEEDED. You have to call something:

    085   seed_wall_defaults(company, owner)
          generate_service_milestones(company)
    086   seed_shoutout_categories(company)

    Running 085 and 086 creates the FUNCTIONS. It inserts nothing. Every
    badge, award, recognition value, shoutout category and wall_config row
    comes from calling them, once per company.

    THIS IS THE STEP THAT IS EASY TO MISS. Run all seven files, open the Wall
    of Fame, and it is empty -- not broken, just never seeded -- and it looks
    exactly like a migration that failed.

    Per 085's own usage note, for each company:

        select seed_wall_defaults('<company_uuid>', '<hr_head_employee_uuid>');
        select seed_shoutout_categories('<company_uuid>');
        select generate_service_milestones('<company_uuid>');

    then, in the same admin session, flip the master switch:

        update wall_config set module_enabled = true
        where company_id = '<company_uuid>';

    There are three companies in this database, so that is three passes. Get
    the UUIDs with:

        select id, company_name from companies order by company_name;

    and the HR head's employee id with:

        select id, full_name, emp_code from employees
        where company_id = '<company_uuid>' and date_of_leaving is null
        order by full_name;

    seed_wall_defaults returns jsonb saying what it created, so you can read
    the result rather than guess. It is safe to call twice -- everything
    inside is ON CONFLICT DO NOTHING.

ALREADY IN THE DATABASE, nothing for you to do:

8. THE RULE THAT MUST NOT MOVE
--------------------------------------------------------------------------------

pms_policies.payout_linkage_enabled is pinned false by a CHECK constraint:

    payout_linkage_enabled boolean NOT NULL DEFAULT false
                           CHECK (payout_linkage_enabled = false)

The PMS is developmental. The rating has no link to increment, variable pay,
bonus, or CTC, and additional benefits are recognition only -- certificate,
nomination, award, no cash component. Enabling linkage would take a migration
that drops the constraint, which is a product decision rather than a config
one. Leave the constraint where it is.


--------------------------------------------------------------------------------
9. IF SOMETHING GOES WRONG
--------------------------------------------------------------------------------

Every file is idempotent, so the first move is almost always to fix the cause
and run the whole file again rather than to unpick a partial run.

  PGRST205 in the app after a migration ran cleanly
      PostgREST's schema cache has not caught up. Wait, or reload it from the
      dashboard.

  42501 permission denied
      A grant is missing, not a policy. See section 5 -- the error text names
      the exact statement that fixes it.

  42P01 relation does not exist, mid-file
      Run order. Check 082-before-084 and 084-before-085/086/087.

  Wall of Fame empty after everything ran cleanly
      You have not called the seed functions yet. Section 6.

  Anything you would rather not decide alone
      Send it to me with the error text and I will look. Do not work around a
      constraint to make a file run -- the constraints are load-bearing, and
      one of them (section 8) is a product commitment.
